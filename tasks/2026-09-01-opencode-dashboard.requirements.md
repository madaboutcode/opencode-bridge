## 1. Architecture & Scope

- R1: System is a standalone TUI binary `dashboard` in same repo as `opencode-mcp`, sharing lib `crates/opencode-client` for auth + `GET /api/session` + `GET /api/session/{id}/message` + `GET /api/event` SSE. Source: user confirmed B1, two mains sharing lib, no bloat.
- R1.1: `opencode-client` has no TUI deps (no ratatui) and no MCP deps (no rmcp). `dashboard` depends on `client + ratatui + crossterm`, `mcp` depends on `client + rmcp`. Source: user "without making either one bloated".
- R1.2: Dashboard talks directly to opencode server `127.0.0.1:49374` via `service.json` password, independent of MCP process. MCP tag (`via MCP` pill) is bonus enrichment if metadata present, not required. Source: Q2 follow-up + advisor.
- R1.3: **[NEW 2026-09-02]** Dashboard core is harness-agnostic. It depends on a `HarnessAdapter` abstraction, not directly on `opencode-client`'s wire shapes, for anything that touches session state or rendering content. An adapter's sole job: watch its harness however that harness requires (opencode: REST + SSE, R4; a future hook-based harness: a local listener its hooks POST to; another: file-tailing — mechanism is entirely the adapter's choice and invisible to the core) and produce session snapshots (R1.4) in the shared shape. All harness-specific interpretation lives inside the adapter, not the core — this includes: the `needs-you`/question-detection heuristic (R6.7, opencode-specific guesswork with no real wire signal; a harness with an actual "waiting on you" signal reports it directly, not re-derived from text), the `call_id → name` tool correlation (R6.4), and tool-name-to-action-line rendering (R6.5/R6.6). The core only ever receives the already-rendered result (e.g. `current_action: "editing: foo.rs"`), never a raw tool name/args pair — this stops a second harness's tool vocabulary from leaking into the shared model through the back door. V1 builds exactly one adapter (opencode, per R4/R6.4/R6.5 as already specified) registered against this boundary; nothing else is implemented, but the core model must not assume SSE, a REST reconcile sweep, or any other opencode-specific mechanism exists. Source: advisor review of this design, this session.
- R1.4: **[NEW 2026-09-02]** Adapters push **session snapshots**, not fine-grained events: the full current state of one session (upsert, keyed by session identity R1.5) or an explicit "session gone" message, on one shared channel. The core stores only the latest snapshot per key, bucketed by project (R1.6), and recomputes layout every frame from current snapshots — consistent with R5.4/BRIEF-v2's existing "no caching, no stability logic" behaviour. Rejected alternative: a fine-grained normalized event stream (session created/updated, tool-call started/finished, etc.) — dropped because an adapter already has to keep this same per-session state itself to build things like the recent-actions ring and files-touched list (R5.3), so an event stream would fold that state a second time in the core for no benefit. At real usage scale (R5.8, ~8 sessions, 250ms redraw) snapshot chattiness costs nothing. Source: advisor review.
- R1.5: **[NEW 2026-09-02]** Session identity = `(harness kind, harness-native session id)`. No cross-harness reconciliation logic in the core — if a harness's own resume/restart behaviour produces a new native id for what a user would consider "the same session," making that continuity visible (or not) is that harness's adapter's problem, not the core's. Nickname hashing (R6.8) uses this full tuple, not the raw id alone, so two harnesses can't collide on id format. Source: advisor review.
- R1.6: **[CONFIRMED 2026-09-02 by spike, see `tmp/2026-09-02-project-identity-spike/EVIDENCE.md`]** Project identity = the canonical git repository toplevel path of the session's working directory; if that directory isn't inside a git repo, fall back to the canonicalized working directory itself — never an adapter-specific placeholder (e.g. opencode's own `"global"` project id). Canonicalize (resolve symlinks, strip trailing slash, normalize case on case-insensitive filesystems) before comparing paths — canonicalize git's own `--show-toplevel` output too, not just the input path (both need it, e.g. macOS's `/var` → `/private/var`). Consequence, confirmed by user: two git worktrees of the same repository get **separate** project boxes (different toplevels) — no worktree-merging logic. A session launched in a monorepo subfolder is grouped under that repo's single project box, not split out per subfolder. A subagent/child session inherits its parent's `location.directory` exactly, so it always lands in the same project box with no special-casing needed at this layer. Source: user decision, this session — "git repo root but fall back to working dir if not present" for project scope; "separate boxes" for worktrees. Confirmed against real opencode sessions and filesystem fixtures (repo root, subfolder, parent+subagent, explicit bridge `directory` param, symlink, two worktrees) by the T01 spike, 2026-09-02 — all 9 checks matched. One clause remains untested: case normalization on a case-insensitive filesystem, because the spike's build machine (macOS APFS) is case-preserving and produced no real case mismatch to exercise (see OPEN items). **Implementation note for `client.md` (M2), flagged by advisor at M1 milestone review:** resolving to git toplevel is a subprocess spawn (`git rev-parse --show-toplevel`); a session's directory→toplevel mapping is stable for that session's lifetime, so the resolver must cache it per session rather than re-spawning on every snapshot/redraw — the spike measured correctness only, not call frequency, and this was never stated as a requirement.
- R1.7: **[NEW 2026-09-02]** No session may go silently stale forever because a push-only adapter missed a message. Opencode's adapter gets a free safety net from its own 60s REST reconcile sweep (R4), but a hook-push-only adapter has no REST to reconcile against. The core requirement, independent of any adapter's transport: track time-since-last-snapshot per session, and treat one that's gone quiet past a threshold as stale rather than assuming it's still accurate forever. Exact threshold/UI treatment is an implementation detail, not decided here. Source: advisor review — flagged as "the item most likely to break silently."
- R1.8: **[NEW 2026-09-02]** When sessions from more than one harness kind are present at the same time, each tile reserves a small glyph/tag slot identifying its harness — exact glyph and placement is an R5.3/R6 tile-content-ladder detail, not decided here, but the slot must exist so this isn't a retrofit later. Hidden/absent when only one harness kind exists in the current data (V1 default: only the opencode adapter exists, so this never shows yet). Source: user decision, this session.
- R2: Dashboard follows ratatui + crossterm TUI best-practices: alternate screen + raw mode + hide cursor with Drop/panic restore, `crossterm::event::poll(250ms)` + `KeyEventKind::Press` only, SSE via tokio mpsc, `terminal.draw` tick, resize handling, Style via ratatui. Source: user "follow tui best-practices".

## 2. Data & Active Window

- R3: **[REVISED 2026-09-02]** Active session = time-since-last-snapshot-received (R1.4) within window `W` minutes (`now - last_snapshot ≤ W`), not opencode's specific `session.time.updated` field — an adapter may pass a harness-native timestamp in the snapshot if it's more accurate than dashboard receipt time, but the core's window logic is transport-agnostic. Source: user Q1 "ues updated within last 10m"; genericised per R1.3's harness-agnostic core.
- R3.1: Default `W = 10m`. Changeable in UI via keyboard (R8). Source: user "show session active in the last 10mins let's say - changeable in the ui using keyboard shortcuts".
- R3.2: Idle session = `updated` outside `W` (but still exists on server). Idle never hidden silently when its project has at least one active session — see R5.2. Source: grill-me Q4 + advisor "idle as context".
- R4: **[opencode-adapter-specific detail, not a core requirement — see R1.3]** The opencode adapter fetches all sessions via `GET /api/session` (paginated) and per-session details on zoom, keeps them live via `GET /api/event` SSE + 60s periodic sweep reconcile, and emits session snapshots (R1.4) from the result. Correctness from polling, SSE for latency (same as `SPEC.md:7` bridge). This reconcile mechanism is specific to having a pollable REST API — a push-only adapter (e.g. hooks) has no equivalent and relies on R1.7's staleness rule instead. Source: codebase scan.

## 3. Layout (area-proportional "Mosaic" — CONFIRMED 2026-09-02)

- R5: **[CONFIRMED 2026-09-02]** Layout is the area-proportional "Mosaic": one `squarify()` call packs project regions into the body area (weight = session count, R5.1), a second `squarify()` call per region packs that project's active session tiles (weight = content demand, R5.2), and tile content scales with the space it's actually given (R5.3). Verified against a real ratatui build and render evidence, not a mockup — see `tmp/20260901-prototype-dashboard-layout/renders/`. This replaces the 2026-09-01 flow-grid design (fixed-size cards, tight-fit boxes) outright — that design left most of the screen blank at real usage scale (R5.8) and is not being revisited (see handoff Dead Ends, session 2026-09-02). Source: advisor + fable-redesign exploration, built by `mosaic-coder`, reviewed via `/refine-loop`.
- R5.1: **[CONFIRMED 2026-09-02]** Project region weight = number of top-level sessions currently shown, all states; subagents never count toward weight — they're content inside the parent session's tile, not a separate region. All-idle projects are excluded from the treemap entirely, shown only in the footer (`hidden: name (N idle)`). Squarify input order is first-appearance order, never weight-sorted — kept because a weight-sort separated project regions the user needed to compare side by side, not (as first reasoned) to hold screen position: R5.7 no longer promises that. Source: Mosaic build + review.
- R5.2: **[CONFIRMED 2026-09-02]** Session tile weight = content demand, not status (R6.1 still holds — status is colour/glyph/order, never geometry): idle = 1, running/needs-you/question = 2, +1 per subagent. Idle sessions are pulled out of the tile-squarify call entirely and shown as a single chip row (`○ nick · age`, overflow `+N idle`) on the region's last row instead of being tiled — fixed a real case where a lone idle tile was the largest blank block on screen. Squarify then runs over active sessions only. Source: Mosaic build + review; idle-chip-row idea borrowed from concept-image review.
- R5.3: **[CONFIRMED 2026-09-02]** Tile content is a total function of the tile's own inner width/height, not fixed lines: colour-only below a minimum width, up through single glyph/age, up through a 3–4 line "compact" form, up to an "extended" form of priority content blocks (title, current action, subagent lines, wire title, files touched) plus one elastic block that absorbs whatever rows are left (recent-actions list for running tiles, tail-kept final assistant text for question/needs-you/idle tiles). Full regime table and per-state block order: `tmp/20260901-prototype-dashboard-layout/BRIEF-v2.md`. Source: user, "the smart/genius lies in using the space... without making it cluttered"; verified against a real render where fixed-line cards left blank space below the text.
- R5.4: Viewport is `frame.area()` from ratatui. Grid recomputed on every `Resize` event and on every change where classification/membership/weight/order actually changes. Viewport scaling: larger terminal fits more project boxes per row / more cards per box, not stretched empty boxes.
- R5.5: Minimum sizes (advisor): session card outer `12×5` cells (`10×3` usable after border) — recheck against 3-line card, may shrink now the 4th line is cut. Project box needs `14×7` or it collapses to one project-summary tile (name + status counts). Below `40×12` viewport, show centered `terminal too small` panel. Never draw unreadable slivers. Source: advisor Sol.
- R5.6: **[REVISED 2026-09-01]** Visible set per project: max 3 cards. Order for visible 3 = `needs-reply first (R6.7) → longest-waiting next → running → most recent idle`. `stalled` removed — no wire signal exists for it (status-signals spike). Beyond 3, collapse remainder into one overflow chip `+N idle` / `+N sessions`, tiny, not weighted. Subagents (`parentID` children) are first-class cards with `↳` prefix, not a third level. Source: Q4 + advisor; stalled removal per advisor + status-signals spike.
- R5.7: **[REVISED 2026-09-02 — original pick retracted]** Project region screen position is **not** guaranteed stable. Squarify has no positional-stability guarantee: a mutation test on the real Mosaic build (add sessions, add a project) moved 3 of 4 project regions to a different screen column — not just a resize. On-screen reading order is likewise not guaranteed to match first-appearance/list order (same root cause: squarify preserves input *order* for its packing algorithm, not final on-screen *position*). The 2026-09-01 pick ("stable slots over priority reflow") is retracted: area-proportional packing at real usage scale (R5.8/R5.9) is worth more than positional memory. Source: user ruling on the Mosaic mutation-test evidence, 2026-09-02 — "accept the motion."
- R5.8: **[NEW 2026-09-02]** Real usage scale is small: typically **2 sessions per project, 4 projects max at a time** (~8 sessions total), not the 10–50+ session stress cases earlier drafts and spikes were tuned against. This governs which layout tradeoffs actually matter for V1: a dense list-style layout's caps/overflow logic (R5.6-style demotion, `+N` chips) never fires at this scale, so a layout built only for scale-safety renders most of the screen blank. Stress scale must still not break badly (secondary check), but is not the design target. Source: user, this session — corrected an assumption several earlier spikes and the fable-redesign exploration were implicitly built around.
- R5.9: **[FOLDED INTO R5/R5.1 above, 2026-09-02 — confirmed by real build]** Kept for provenance: project box area ∝ session count via one squarified-treemap call (Bruls et al., unmodified algorithm). Why it's back after R5.1/R5.3's 2026-09-01 retirement: at real scale (R5.8), a flow-grid/list layout leaves most of the screen empty (measured: 3 of 4 candidate layouts used ≤13 of 40 available rows at 4 projects/8 sessions; only the area-proportional one used all 40 — see `redesign-specs.md` §"Real-scale findings"). Source: fable-redesign exploration + this session's squarify-based spike.
- R5.10: **[FOLDED INTO R5/R5.3 above, 2026-09-02 — confirmed by real build]** Kept for provenance: card/tile content scales with the space it is actually given, a growth ladder rather than a fixed line count. Confirmed against a real render where fixed-3-line cards inside a bigger proportional box just left blank space below the text (`tmp/20260901-prototype-dashboard-layout/shots/C-real-wide.png`, pre-fix).
- R5.11: **[CONFIRMED 2026-09-02]** Project accent colour is applied to **one small element only** (the project name/tag), never to a whole card or project border. Six saturated project borders compete with the state colours (running/needs-you/idle) that are supposed to carry attention, and were flagged as the reason "nothing pops" in the pre-Mosaic build. Revises R6's "border color per project" default below. Source: fable-redesign exploration; verified in the Mosaic build (no borders at all — tile background carries state, badge carries urgency).

- R6.3: **[REVISED 2026-09-01]** Each session card shows 3 lines, not 4 — user confirmed by direct pick (title, status+elapsed, current action; cost/tokens NOT picked, cut — also resolves the R10 non-goal contradiction the 4-line version had): (1) title/handle line — content decided (nickname + wire title, R6.8), exact arrangement (border title vs. shared line) pending R6.2 chrome axis; (2) status word + elapsed per R6.7 (`needs-you · question`, `needs-you · 14m`, `running · 2m ago`); (3) current action — last tool call or file touched, one line, truncated (R6.4/R6.5). - R6.4: **[DECIDED 2026-09-01; internals reassigned to the opencode adapter, see R1.3]** "Current action" text (R6.3 line 3) is populated by subscribing to `GET /api/event` (SSE) and tracking tool events client-side per session — not by polling `GET /api/session/{id}/message` per tile. Confirmed field shapes in status-signals spike addendum: `session.tool.input.started` carries `{id, name}`; `session.tool.called` carries `{id, input}` (no name). The opencode adapter keeps a per-session `call_id → name` map, populated on `input.started`, consumed on `tool.called` to build the display line, dropped once consumed — the core dashboard never sees the raw SSE events or the map, only the already-rendered line in the session snapshot (R1.4). This is in addition to the existing SSE consumption already speced for terminal `session.execution.*` events (R4).
- R6.5: **[NEW 2026-09-01, phase 1]** Coarse tool → action-line mapping, built only from tool names confirmed on the wire so far:
  - `shell` → `input.command`, single line, collapse newlines to ` · `, truncate to tile width with `…`.
  - `edit` → `editing: ` + basename of `input.path` (fall back to full relative path if it fits).
  - any other/unrecognized `name` → `running: <name>` (generic fallback, no arg parsing).
  Action line updates on each `tool.input.started`→`tool.called` pair; holds its last value between tool calls until the next one arrives or the session's terminal `session.execution.*` fires (then line 3 clears or shows outcome — TBD at implementation). No per-tool detail beyond this (no diff preview, no truncated grep pattern, etc.) — that's phase 2.
- R6.6: **[REVISED 2026-09-01, phase 2, OPEN]** Full tool-name vocabulary confirmed: `shell, edit, grep, write, skill, subagent, glob, patch, read`. - R6.7: **[REVISED 2026-09-01, CONFIRMED FINAL; question-detection internals reassigned to the opencode adapter, see R1.3]** Attention model is 3 states, named to say who's waiting on whom (`waiting` was ambiguous — old R6 used it as a machine state; renamed): `running / needs-you / idle`. This 3-state model is the core's vocabulary, harness-agnostic. `stalled`/hang-timeout heuristic is explicitly NOT V1 — user confirmed directly (asked point-blank "have you ever had a session actually hang, vs finish and sit waiting" — answer: no) that this is a real reduction against what the original R6 implied, not a free simplification, and accepted it on that basis.
  - **running** — turn in progress (`outcome` absent on REST; between `session.execution.started` and its terminal). Card shows live action line (R6.4/R6.5). Not urgent.
  - **needs-you** — turn ended (`outcome` present, `time.idle` set). Two visual sub-states, same underlying status:
    - **question badge** — the ended turn's final assistant text looks like a question (heuristic: ends in `?`, or matches a short phrase list — "which", "should I", "do you want", etc. — exact list still an OPEN implementation detail). Detected by fetching the last assistant message ONCE on the session's transition into idle (not per poll). Shown with a distinct badge/color, sorted first (R5.6) — this is the case the user called out directly: "if it's waiting with a tool call for ask question... that should be prominently highlighted." Confirmed live: a session told to stop and ask a clarifying question ends with plain `outcome:"succeeded"` + `time.idle` — wire-identical to a normal completed turn; the heuristic on final text is the only way to tell them apart, since opencode2 has no permission/ask-question protocol signal (spiked directly, see the SSE event-catalog doc).
    - **needs-you `Nm`** — ended turn, heuristic didn't match. Elapsed since `time.idle` shown directly; the number itself is the urgency ordering, no separate "stalled" tier needed.
  - **idle** — outside the active window `W` (R3.2). Only shown as context inside a project that has ≥1 running/needs-you session, or collapsed into the overflow chip.
  Source: advisor recommendation (3-state, built only from confirmed fields, correct naming) + user direct pick (heuristic-now) + live spike confirming no distinct wire signal exists for "asking a question" + user's direct confirmation no hangs have been observed.
- R6.8: **[REVISED 2026-09-02 — replaces the 2026-09-01 adjective+noun scheme below; reverses its "determinism over uniqueness" rule, see rationale]** Card title/identity: a single word from a categorized, curated wordlist (famous people, fictional characters, etc. — one category per file, no adjective+noun combining). **No combining, single word only** — this is a user decision, 2026-09-02.

  **Two-layer "seat" claim scheme**, both layers using the same mechanism:
  1. **Project → category.** Each currently-live project claims one category, exclusively, for as long as it has at least one live session. Preferred category = `hash(project identity, R1.6) mod category count`; if that category is already claimed by another currently-live project, claim the next available one instead (deterministic scan order, e.g. next index, wrapping). Released when the project has no live sessions left.
  2. **Session → word (seat) within its project's claimed category.** Preferred word = `hash(harness kind, native id — the R1.5 session identity) mod word count` — scattered across the category's list by hash, not a fixed `word[0], word[1], ...` walk-order, so usage doesn't concentrate on the same couple of names for every project (user decision, 2026-09-02: variety over concentration). If the preferred word is claimed by a live sibling, or is in cooldown (see below), deterministically probe (secondary hash-derived stride, not true randomness — see rationale) to the next word that is both free and off cooldown. **Recycling:** a departed session's word does not return to the available pool immediately — it enters cooldown and isn't claimable again until enough other distinct words in that category have been claimed since (a small per-word "last freed" counter compared against a per-category claims-since counter — bounded state, no historical log), so a name doesn't start silently pointing at a different session shortly after the original one ends.

  **Guarantees, both hard (not low-probability):** no two sessions in the same live project ever show the same name; no two live projects ever show the same name. Both guarantees assume (a) live project count never exceeds the curated category count, and (b) no word is duplicated across two different category files — both are content-curation/capacity constraints on whoever authors the wordlists and category count, not runtime checks (see Open Questions for the capacity edge case).

  **This reverses the 2026-09-01 decision below** to accept collisions and explicitly forbid render-time collision-fixing. That decision was right for *its* scheme — adjective+noun gave a combinatorially large space, so collisions were rare and cheap to accept. It doesn't hold for a single word drawn from one category's list at real session counts: birthday-paradox math makes same-project collisions common, not rare, once the word list shrinks to single-word scale. The new scheme also deliberately drops "pure function of session ID alone, no storage, no cache" — provably, any naming scheme that is both collision-free and holds a name for a session's whole lifetime must depend on arrival history (who else was live, and when), not just the session's own id: if two sessions prefer the same word, whichever one doesn't get it must show something that isn't explained by its own id alone. Source: advisor review + brainstorming session, 2026-09-02.

  **Coupling to R1.7 (not yet resolved there):** both claim layers (project→category, session→word) must release their claim on whatever R1.7's eventual staleness rule decides, not only on an explicit "gone" message — otherwise a session or project that goes silently stale without a tombstone holds its claim (and its seat) forever, leaking the pool. Flagged here so the coupling is visible when R1.7 gets designed, rather than discovered later.

  **Word list content:** **10+ categories** (user decision, 2026-09-02 — more headroom against the project-count capacity edge case below than the coordinator's original 6-category proposal), each its own file, proposed by the coordinator and approved/edited by the user, then frozen. Freezing (per the 2026-09-01 rule, still true) now applies at two independent levels: the category list itself, and each category's word list — changing either after V1 reshuffles claims for whoever currently holds a seat depending on ordering.

  **[2026-09-01, superseded above]** Original rule was: deterministic per-session nickname (adjective+noun, both words ≤6 chars), hashed from the full session identity `(harness kind, native id)` (R1.5). Pick determinism over on-screen uniqueness (accept collisions — two same-named cards still differ by project/title/status/action; do NOT "fix" collisions by appending hash chars at render time). Curate for visual/phonetic spread so near-neighbors like `brave-otter`/`brash-otter` don't read as the same card. Kept for provenance only — retracted 2026-09-02.

  Placement is NOT a free 5th axis — it's a consequence of the chrome axis (R6.2/prototype): bordered cards put the nickname in the `Block` title (ratatui already specs `Block::bordered().title(...)`, zero body-row cost); boxless cards share line 1 as `nickname · title`, truncated. Wire title itself stays as the descriptive line, still shown per R6.3. Exact category set/word lists are the next deliverable, not yet open design questions.
