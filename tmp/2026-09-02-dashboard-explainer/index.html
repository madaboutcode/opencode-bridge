Design explainer — opencode-mcp

opencode-dashboard

A full-screen terminal view that shows every coding-agent session you have running, across every project, at once — and tells you which ones are waiting on you.

Status of this design

Nothing is implemented. This is a spec, not a program. Two things are settled by evidence rather than opinion: the layout was built as a real ratatui program and reviewed against its render output (R5–R5.11), and project identity was confirmed against real opencode sessions and filesystem fixtures (9 checks, R1.6). The multi-harness architecture (R1.3–R1.8) is designed and reviewed but unbuilt: opencode is the only adapter that exists.

1The problem, and who it's for

You run several coding agents at once, in different repositories, in different terminals. Each one is a separate process you have to go and look at. The expensive question is not “what is this agent doing” — it is “is anything waiting on me?” Answering that today means visiting every session in turn, and the cost of a forgotten session is idle time you can't get back.

The dashboard is one screen that answers that question without a single keypress R7. Every active session across every project is on screen at the same time, grouped by project, each one showing whether it's running, waiting on you, or gone quiet.

Three properties fall out of that framing and drive almost every decision downstream:

  • Attention, not analytics. The screen is organised around who is waiting on whom. Cost, tokens, and diffs are all explicitly out of scope R10.
  • Area is the scarce resource. With a handful of sessions and a whole screen, the interesting design problem is how a tile grows into the space it happens to get R5.3.
  • Keyboard only. Every control is reachable without a mouse R10.

It is deliberately not a general session manager: no pagination beyond the live window, no git history, no mouse interaction R10. It is a glanceable attention surface.

2Two binaries, one library

The dashboard is its own program in the same repository as the existing opencode-mcp MCP server, not a mode of it R1. The two share one library, crates/opencode-client, which owns talking to the opencode server: authentication, the session list, session messages, and the event stream.

The point of the split is dependency hygiene R1.1:

Who links what.
CrateDepends onDeliberately does not depend on
opencode-clientHTTP + SSE + authno ratatui, no rmcp
dashboardclient + ratatui + crosstermno MCP toolkit
mcpclient + rmcpno TUI toolkit

The dashboard connects straight to the opencode server on 127.0.0.1:49374 using the password the server itself writes to service.json — it does not need the MCP process running R1.2. If session metadata happens to show a session was started via MCP, the dashboard shows a small via MCP tag as a bonus; its absence changes nothing else about how that session is displayed.

Standard terminal-app discipline applies R2: alternate screen and raw mode, cursor hidden, and the terminal restored on exit even if the process panics; a 250 ms poll() rather than busy-waiting; resize handled; KeyEventKind::Press only, so a held key doesn't fire repeatedly.

3The number that governs everything

R5.8 — real usage scale

Typically 2 sessions per project, 4 projects at a time, ~8 sessions total. Not 10, not 50+.

This single correction is worth more than any other note on this page, because several earlier drafts and spikes were implicitly tuned against a 10–50 session stress case and were wrong for it. The measurable consequence: at 4 projects and 8 sessions, three of four candidate layouts used 13 of 40 available rows at most. Only the area-proportional layout used all 40 R5.9.

That is why the layout is built around filling the screen rather than around overflow-safety. At this scale the per-project 3-tile cap and its overflow chip essentially never fire R5.8. Larger scale must still not break badly — but it is a secondary check, not the design target.

5How the design is documented

The design lives in five spec files, split by concern rather than by feature. Every requirement has a stable number — R5.2, R6.8 — that other specs, QA artefacts and code comments cite directly. Numbers are never renumbered; if a requirement is superseded it says so in place and keeps its number.

The spec tree under docs/specs/dashboard/.
FileOwns
overview.mdScope, the two-crate split, the harness-agnostic core boundary (summary), the active/idle window, real usage scale, non-goals — R1, R3, R5.8, R10
client.mdThe HarnessAdapter contract in full, session snapshots, session and project identity, staleness, and the opencode adapter's own REST/SSE mechanics — R1.3–R1.8, R4, R6.4–R6.6
layout.mdThe Mosaic: weighting, squarify packing, tile content scaling, minimum sizes, degrade states — R5, R9
visuals.mdChrome, card content, the attention model, the naming scheme — R6
interactions.mdKeyboard navigation, zoom, window controls — R7, R8

Two conventions make these specs safe to implement against:

  • One scenario per requirement, co-located. Every requirement is followed immediately by its own Given / When / Then — the primary happy path written right where the rule is, not in a separate QA file.
  • Unresolved questions are marked, not silently answered. An open question carried forward from the source material is written as [REVIEW: …] next to the requirement. Writing the spec does not license the writer to pick an answer; that is a design decision, not a transcription one. This explainer marks those the same way — see below.

6What is still open

Twelve items are genuinely undecided. They are listed here because a reader who assumes the design is finished will be wrong about something specific.

Open questions, roughly in order of how much they block an implementer.
#Open itemReq
1Card chrome. Three options under test — (A) border on project box and card, (B) no borders anywhere, colour stripe plus header line, (C) border on project box only. This is the live prototype axis. It must be settled by a runnable render in the user's own terminal, because a text mockup would rig the comparison: box-drawing characters survive as plain text, while B's entire grouping signal is colour.R6.2
