Layout

The Mosaic

One squarify() call packs project regions into the body area. A second call packs each project's session tiles inside its own region. Tile content then grows into whatever space the tile actually got.

1The idea

The screen's body area is packed by an area-proportional algorithm — squarify, the Bruls et al. squarified-treemap algorithm, used unmodified R5. It is applied twice:

  1. Pass 1 divides the body area into one rectangular region per project. Weight = that project's session count R5.1.
  2. Pass 2 runs again, separately inside each region, dividing that region's area among its session tiles. Weight = content demand R5.2.
  3. Tile content is then a function of the size the tile ended up with R5.3. There is no fixed card size anywhere in the system.
Why it replaced the earlier design

This replaced a fixed-size-card “flow-grid” design outright, and the reason is a measurement rather than a taste: at real usage scale (4 projects, 8 sessions), three of four candidate layouts used at most 13 of 40 available rows. Only the area-proportional layout used all 40 R5.9. A later render also caught the mirror-image failure — fixed 3-line cards sitting inside a large proportional box, leaving blank space below the text — which is what the content ladder in §5 exists to fix R5.10. The earlier design is not being revisited.

2A screen, assembled

A 120 × 34 cell body area with four projects and eight top-level sessions. Project weights are 3 / 2 / 2 / 1; a fifth project, epsilon, has only idle sessions and so never gets a region at all.

Things worth reading off this picture:

  • Region widths are 45 / 30 / 30 / 15 out of 120 — exactly proportional to the weights 3 / 2 / 2 / 1, since all four are full height.
  • Two tiles share alpha's region, packed with weights 3 / 2 because the first session has a subagent.
  • Nothing is wasted. Every cell belongs to a tag row, a tile, or an idle chip row.
  • The narrowest tile (scratch, 13 cells of inner width) drops to the shortened status line run · 3m instead of running · 3m.
  • epsilon has no region — it is all-idle, so it exists only in the footer.

3Pass 1 — project regions

R5.1 — what feeds the first squarify call.
RuleDetail
WeightNumber of top-level sessions currently shown, counting all states — running, needs-you and idle.
SubagentsNever add to a project's weight. A subagent is content inside its parent's tile, not a region of its own.
All-idle projectsExcluded from the packing entirely. They appear only in the footer as hidden: <name> (N idle).
Input orderFirst-appearance order, never weight-sorted.
EdgesAdjacent regions snap to share exact edges — no visible gap, no overlap.
Why first-appearance order, and why that reason changed

The ordering rule is kept because a weight-sort separated two project regions the user needed to compare side by side. Note what it is not kept for: the original justification was to hold screen position, and that justification was retracted when a mutation test showed squarify gives no positional stability anyway (§7). The rule survived; its reason was replaced.

R6.1 — status never drives geometry

Attention state is expressed through colour, glyph and sort order only. A needs-you tile is never drawn larger than a running one just because it is more urgent. Making urgent tiles bigger is a rejected V2 idea R10.

Idle sessions are not tiles at all

Idle sessions are pulled out of the tile packing entirely and rendered as a single chip row on the region's last row: ○ nick · age, separated by two spaces, most-recent-first. Overflow becomes +N idle, and space for that is always reserved R5.2. Only active sessions get packed into tiles.

Why

A lone idle tile was the largest blank block on screen in testing. It had the least to say and, being untethered from content, it held area that a content-bearing tile could have used.

Region-height thresholds for the idle row R5.2.

h ≥ 3tag row + tiles + idle chip row
h = 2tag row + tiles; the idle row is dropped and its count folded into the tag row
h = 1tag row only

And one precedence rule: if reserving a row for idle chips would leave no room for tiles, the idle row is dropped first. Tiles outrank chips.

  • needs-you counts since the turn ended.
  • running counts since the current turn started.
  • idle counts since the session's last update.
  • If a session has subagents but there is no room for dedicated subagent lines, the status line gets a ↳N suffix — but only when at least 4 cells remain on that line.

Compact form R5.3 — wi ≥ 12, h = 3–4

  1. glyph nick, bold, in the state's colour.
  2. One content line, truncated with … — question: first line of the final assistant text · running: the current action · needs-you (plain) and idle: the wire title.
  3. The status line.
  4. Only if h = 4: the first subagent line ↳ nick action, truncated — otherwise blank.

6The extended form

For wi ≥ 12 and h ≥ 5, the tile is built from priority content blocks plus exactly one elastic block that absorbs whatever rows are left. Priority 1 is never dropped. If the fixed blocks alone don't fit, blocks are dropped from the bottom of the priority list until what remains fits.

Text word-wraps to wi, hard-breaking a single word longer than wi. A block wraps when it has more than one row available and truncates with … when it has exactly one.

The rule that keeps it honest

Any rows left after the elastic block runs out of content stay tinted blank. No filler, no decoration. Filling 100% of the screen is the lowest-priority goal in the whole layout (§8).

Running

  1. glyph nick, bold
  2. current action — wraps up to 2 rows
  3. status line
  4. one line per subagent: ↳ nick action, truncated
  5. (blank row +) wire title, dim, up to 2 rows
  6. (blank row +) files: a.rs, b.rs, …, dim, up to 2 rows — omitted entirely if no files were touched this turn
  7. elastic — recent-actions list: entries before the current action, so block 2 is never repeated. Oldest first, dim, with the most recent 2 entries shown brighter.

Question

  1. glyph nick, bold
  2. the question badge
  3. (blank row +) elastic — final assistant text, wrapped. On overflow the tail is kept, because the question is at the end, and the first shown row becomes ⋯.
  4. (blank row +) you: <last user prompt>, dim, up to 3 rows
  5. (blank row +) wire title, dim, up to 2 rows
  6. subagent lines — rare here, so they sit after the title

Drop order when things don't fit: 6, then 5, then 4. The elastic block always keeps at least 1 row as long as h ≥ 3.

Needs-you (plain)

  1. glyph nick, bold
  2. wire title, up to 2 rows
  3. status line
  4. subagent lines
  5. (blank row +) elastic — final assistant text (what the session finished), tail-kept with ⋯ on overflow
  6. (blank row +) you: <last user prompt>, dim, up to 3 rows

Idle

  1. glyph nick, dim bold
  2. wire title, dim, up to 2 rows
  3. status line
  4. (blank row +) elastic — final assistant text, dim, tail-kept

Recompute rules R5.4

The grid is recomputed on every resize, and on every redraw where a session's classification, project or tile membership, weight, or ordering has actually changed. There is no caching anywhere in the layout. A larger terminal fits more regions per row and more tiles per region — it never just stretches the existing boxes into empty space.

7Position is not stable — on purpose

R5.7 — a deliberate reversal

Project region screen position is not guaranteed stable, and on-screen reading order is not guaranteed to match first-appearance order either. Do not implement any compensating logic — sticky slots, position memoisation, or anything else. It was considered and explicitly rejected.

The evidence is a mutation test on the real build: adding sessions, then adding a project, moved 3 of 4 project regions to a different screen column — not just to a different size — on the very next redraw.

Why it was accepted

The root cause is that squarify preserves input order for how it packs regions, and packing order is not the same thing as final on-screen position. An earlier decision — “stable slots over priority reflow” — was retracted on this evidence. The user's ruling: accept the motion. Area-proportional packing at real usage scale is worth more than positional memory.

Caps and overflow R5.6

At most 3 session tiles per project. Visible three are chosen in this order:

  1. sessions needing a reply (the question badge)
  2. longest-waiting needs-you
  3. running
  4. most recently updated idle

Everything past the visible three collapses into one small, unweighted overflow chip (+N idle / +N sessions). Subagents are shown as first-class tiles with a ↳ prefix inside their parent's content — never as a third nesting level.

The degrade hierarchy R9.2

full session tiles → project-summary tiles → “+N projects” chip → terminal too small

The priority behind that order, most important first:

  1. Readability
  2. Project presence — every project stays visible in some form as long as possible
  3. Proportionality
  4. Filling 100% of the screen — explicitly the lowest priority

That last place is load-bearing. The layout will happily leave space unused — tinted blank rows at the bottom of a tile, for instance — rather than break a higher rule to fill it.

Empty state R9

When zero sessions are active in the window, the body shows a centred panel rather than a fill of tiny idle tiles:

No sessions updated in last 10m — 6 older sessions hidden — press ] or a

Idle sessions only ever appear as context inside a project that has at least one active session. This panel is what shows when no project qualifies for even that.

Accent colour goes on exactly one thing R5.11

A project's accent colour is applied to one small element only — the project name in its region's tag row. Never a whole tile background, never a tile border, never a project border.

Why the old default was dropped

Six saturated project borders competed with the state colours (running / needs-you / idle) that are supposed to carry the user's attention, and were identified as the reason an earlier build looked like “nothing pops”. In the current layout there are no borders at all: a tile's background carries its state, and a badge carries urgency.
