Architecture

The adapter boundary

The dashboard's core never speaks a harness's wire protocol. One adapter per coding-agent tool stands between them, and every piece of harness-specific interpretation lives inside an adapter — including the parts that feel universal.

1The boundary

Everything that tracks session state or decides what to render depends on a shared boundary called HarnessAdapter R1.3. An adapter has exactly one job: watch its harness however that harness requires, and produce session snapshots in the shared shape.

2Why it is shaped this way

Four reasons, in the order they bite.

2.1 — A second harness's vocabulary must not leak in through the back door

The core only ever receives already-rendered results. A tile's current-action field contains the string "editing: foo.rs" — never a {tool: "edit", args: {…}} pair R1.3.

Why

A “generic” raw pair looks flexible and is not. The moment the core accepts a tool name and an argument object, every harness's tool vocabulary becomes a case in shared rendering code — and shared code that knows nine opencode tool names is opencode code wearing a disguise. Forcing the adapter to render the line means a new harness adds nothing to the core at all.

2.2 — Harness-specific guesswork stays with the harness

Detecting “this turn ended and the agent is asking you something” is, for opencode, a guess with no real wire signal. A session told to stop and ask a clarifying question ends with plain outcome: "succeeded" and time.idle set — wire-identical to an ordinary completed turn R6.7. The only way to tell them apart is to look at the final assistant text, so that heuristic lives in the opencode adapter. A harness with a genuine “waiting on you” signal reports it directly instead of having its output re-guessed by a heuristic written for a different tool.

2.3 — Transport is not part of the contract

opencode exposes a pollable REST API, so its adapter reconciles every 60 s. A hook-based harness has nothing to reconcile against. The core's data model is therefore forbidden from assuming SSE, a reconcile sweep, or any other opencode-specific mechanism exists anywhere in its shape R1.3.

2.4 — Only one adapter is built

V1 builds exactly one adapter. This is a shape for future adapters, not new V1 scope — and it is deliberately not tested by a second implementation, because there is no second harness to design against yet.

4Snapshots, not events

R1.4

Adapters push session snapshots — the full current state of one session — not fine-grained events. Each message is either a whole-state upsert keyed by session identity, or an explicit “session gone” tombstone. All of them travel on one shared channel.

The core stores only the latest snapshot per key, bucketed by project, and recomputes the layout every frame from whatever it currently holds. It never patches a snapshot incrementally and holds no derived state between frames.

Why not an event stream

The rejected alternative was a normalised event stream — session created, tool call started, tool call finished — mirroring the harness's own wire events, folded into state by the core. It was dropped because the adapter already has to keep that same per-session state itself to build things like the recent-actions ring and the files-touched list. An event stream would fold the identical state a second time inside the core, reconstructing the same snapshot the adapter had already built. And there is no performance case for it: at ~8 sessions redrawn every 250 ms, snapshot chattiness costs nothing.

One consequence worth stating plainly, because it is the kind of thing that gets “optimised” later: there is no incremental update path anywhere in the core. A single changed field arrives as a whole new snapshot.

Not enumerated here

client.md deliberately does not list the snapshot's fields — it owns the delivery contract, and the field contents are specified where they're rendered (visuals.md, layout.md). Reading those, a snapshot has to carry at least: nickname, wire title, status, the rendered current-action line, subagent entries, files touched this turn, final assistant text, last user prompt, a recent-actions ring, an age/elapsed basis, harness kind, project identity, and the last-snapshot time used by R1.7.

5Session identity

R1.5

Session identity is the tuple (harness kind, harness-native session id). The core does no cross-harness reconciliation.

Two harnesses that both happen to mint a session with the native id "123" are two distinct sessions — harness kind is part of the identity, so there is no collision and no merge R1.5. This matters more than it looks: harnesses use small sequential integers, and the nickname hash consumes this full tuple precisely so two harnesses can't collide on id format.

The other half of the rule is a deliberate refusal. If a harness's own resume or restart behaviour mints a new native id for what a user would call “the same session”, making that continuity visible — or deciding not to — is that harness's adapter's problem, not the core's. There is no fuzzy matching layer.

6Project identity

R1.6 — confirmed against real sessions and filesystem fixtures

Project identity is the canonical git repository toplevel path of the session's working directory. If that directory is not inside a git repository, it falls back to the canonicalised working directory itself.

The fallback clause has a specific target: opencode returns the literal project id "global" for any non-git directory, which would collide every non-git session into one bucket. Using an adapter-specific placeholder as a grouping key is forbidden.

Canonicalisation — required before comparing any two paths

  • Resolve symlinks.
  • Strip any trailing slash.
  • Normalise case on case-insensitive filesystems. (Unverified — see open item 11.)
  • Apply the same canonicalisation to git's own --show-toplevel output, not only to the input path. Both need it: on macOS, /var is itself a symlink to /private/var, so an uncanonicalised toplevel and a canonicalised working-directory fallback would silently disagree about the same physical location.
Implementation note — easy to miss

Resolving a toplevel means spawning git rev-parse --show-toplevel. A session's directory→toplevel mapping cannot change during that session's lifetime, so the resolver must cache it per session rather than re-spawning git on every snapshot or every redraw. The confirming spike measured correctness only, not call frequency.

Consequences, all confirmed by the spike

Nine filesystem fixtures — repo root, subfolder, parent + subagent, explicit bridge directory param, symlink, two worktrees. All matched.

7Staleness

R1.7

No session may go silently stale forever because a push-only adapter missed a message. Track time since last snapshot per session; treat one that has gone quiet past a threshold as stale rather than assuming it is still accurate forever.

The opencode adapter gets a free safety net from its own 60-second REST reconcile sweep: a dropped SSE connection self-corrects on the next sweep regardless of this rule. A hook-push-only adapter has nothing to reconcile against, which is exactly what makes this rule load-bearing — it is the only thing standing between a missed message and a session frozen on screen forever.

Open — and coupled to the naming scheme

The threshold and the on-screen treatment (dim it? a distinct state? drop it?) are not decided. Note the coupling: both nickname claim layers must release their claim under this rule, not only on an explicit “gone” tombstone R6.8. Otherwise a session that goes silently stale without a tombstone holds its claimed name forever, leaking it out of the pool permanently.

The harness-tag slot

When sessions from more than one harness kind are on screen at once, each tile reserves a small slot identifying which harness it came from R1.8. The slot is hidden whenever only one harness kind is present — which is every V1 render, since only the opencode adapter exists. Only the slot is required; the glyph and its placement wait for a second adapter to design against.

8The opencode adapter

Everything in this section is adapter-specific, not a core requirement. Nothing here constrains how a future adapter would meet the same contract.

8.1 — How it watches R4

It fetches all sessions via GET /api/session (paginated), fetches per-session details on zoom, and keeps them live via GET /api/event SSE plus a 60-second periodic reconcile sweep.

Which side carries correctness

Polling carries correctness; SSE exists for latency, not as the sole source of truth. So a silently dropped SSE connection shows stale data for at most one sweep interval, then self-corrects. If SSE carried correctness, a dropped connection would be a correctness bug instead of a latency blip.

8.2 — Tool-call correlation R6.4

Two events describe one tool call, and the useful half of the information is split across them unevenly:

session.tool.input.started { id: "call_1", name: "edit" } ← the only event that carries a name session.tool.called { id: "call_1", input: { path: "foo.rs" } } ← carries no name at all ↓ joined by call id, in a per-session map current_action: "editing: foo.rs" ← all the core ever receives

The adapter keeps a per-session call_id → name map: populated when input.started arrives, consumed when the matching tool.called arrives, then dropped. The core never sees the map, the events, the name, or the raw input object — only the rendered line inside the snapshot.

8.3 — Turning a tool call into a line R6.5

The line updates on each input.started → tool.called pair and holds its last value between tool calls, until the next pair arrives or the session's terminal session.execution.* event fires.

The full confirmed vocabulary is nine tools: shell, edit, grep, write, skill, subagent, glob, patch, read R6.6. Seven of nine have confirmed live shapes; glob and patch do not — both were offered to the model in the confirming session and it chose not to use either. Formatting rules for the remaining seven are phase 2; until then the generic running: <name> fallback covers every one of them.
