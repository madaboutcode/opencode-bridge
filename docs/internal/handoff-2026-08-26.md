# Handoff: opencode-bridge (Rust) — MCP server driving opencode2 over HTTP+SSE

A Rust MCP stdio server that gives Claude Code (CC) `Agent`/`SendMessage`-style tools over
**opencode2**, driven entirely through opencode2's **HTTP API + SSE** (no `opencode2 run`
subprocesses). Async tasks push their last-output-before-idle back into the launching CC
session over its inbox socket. This replaces the Python prototype at `~/.opencode-bridge/server.py`.

Built this session by delegating to a `coder` agent (the builder) with a persistent `fable`
advisor running in parallel, per the greybeard/team-lead flow.

## 2. Verified world-facts (conversation-only — expensive to rediscover)

**The opencode2 v2 HTTP API is the whole game — SPEC §1 owns the endpoint list.** Facts that
cost real probing to establish and are easy to get wrong:

- **Discovery:** `opencode2 pair` prints `URLs http://127.0.0.1:<port>` + Basic-auth
  `Username opencode` / `Password <pw>`. Port + password change per service instance — read
  fresh at startup, never cache across restarts. Service must be up (`opencode2 service start`).
- **`/api/event` is ONE global SSE stream for ALL sessions.** Correlation is by ownership:
  we mint every session id via our own `POST /api/session` and filter events by
  `data.sessionID ∈ our registry`. Foreign sessions (TUI, cron, other CC) are dropped. This
  is the real answer to "the server runs other people's tasks."
- **Idle signal = terminal `session.execution.{succeeded|failed|interrupted}`** for our
  session. Observed turn lifecycle: `execution.started → step.started → reasoning.* →
  text.started/delta/ended → step.ended(finish:"stop") → usage.updated → execution.succeeded`.
- **`session.text.ended.text`** carries the finished assistant text; `GET /message`'s last
  assistant `content[]` (concat `type:"text"` parts, ignore `reasoning`) is the authoritative
  final output. Message discriminant is `type:"user"|"assistant"` (NOT `role`), and the list
  is **newest-first** — pick the assistant msg by max `time.created`, don't trust array order.
- **`POST /prompt` is inherently async** — it enqueues and returns the queued user msg
  immediately. `delivery:"steer"` (API default) interrupts the current turn; `"queue"` waits.
  We default `opencode_send` to `queue`.
- **`POST /wait` → 204 when idle** — the sync-path primitive. But a long wait will blow CC's
  MCP tool timeout, so the bridge caps it and degrades to notify (SPEC §7.5).
- **PROBE — subagent completion timing (settled a real risk):** a parent that spawns a
  subagent via the `task` tool blocks on it. Observed: child `execution.succeeded` at
  t=401385ms, parent `execution.succeeded` at t=408040ms (~6.7s later). The child is a
  distinct `ses_id` with `parentID`=parent, so our filter drops the child's terminal event
  (no spurious per-subagent notify). ⇒ the "done" callback fires only when the whole nested
  turn is truly complete. It won't lie.
- **Fast-fail fact:** an invalid agent name (`"Build"` — names are lowercase: `build`,
  `general`) produces an immediate `session.execution.failed` right after `execution.started`,
  before any work. This is exactly the race the register-before-prompt ordering guards.
- **Free test model:** `{"providerID":"opencode-go","id":"ox-alpha-free"}` (`opencode-go/ox-alpha-free`).
  The default `deepseek` key returns `"Insufficient Balance"` 402 — do not test against it.
- **CC callback proven from Rust:** `tokio::net::UnixStream` to `$CLAUDE_CODE_MESSAGING_SOCKET`,
  write auth frame (if `$CLAUDE_CODE_MESSAGING_TOKEN`) then
  `{"type":"user","message":{"role":"user","content":...}}`, `\n`-terminated, then shutdown.
  Bridge processes spawned from a CC-launched context inherit these env vars (Bash children
  see them — that's how the e2e test targeted this session: socket `/tmp/cc-socks/89211.sock`).

**Callback surfacing nuance (cost ~20 min of false-alarm debugging — worth knowing):** a
callback is delivered to the CC session's socket the instant the async task finishes, but it
only **surfaces** (triggers a turn / becomes visible) when the CC session is **idle** between
turns. During a busy session (e.g. an agent mid-tool-calls) callbacks queue and appear
*delayed and out of phase* with whatever you were doing — a followup's callback can surface
during a later, unrelated test window. This is inherent to the peer-message inbox channel,
NOT a bug and NOT lost delivery. Corollary: `notify.rs` logs nothing on success, so an
absent `[bridge] notify:` line in stderr means success, not failure — don't infer a miss
from a quiet log. Also: the pipe-driven test harness closes the bridge's stdin after a fixed
sleep, and stdin-close exits the process immediately (killing the SSE task); if an async turn
outlasts that window the callback is lost — a TEST artifact only, since real CC keeps the MCP
server's stdin open for the whole session.

**Tooling:** rust 1.93.0 / cargo 1.93.0 at `~/.cargo/bin`. opencode2 v0.0.0-beta-17898.
Crates used: tokio, reqwest(json+stream+rustls-tls), serde, serde_json, futures-util — no MCP
SDK (hand-rolled; SPEC §4), no anyhow/thiserror (Box<dyn Error+Send+Sync>).

**zsh gotcha (cost time):** never use `path` as a loop variable in zsh — it's tied to `$PATH`
and clobbering it breaks every subsequent command. Use `ep`/other.

## 3. Decisions & provenance (rationale — SPEC owns the "what")

- **Rust, HTTP+SSE, no subprocess-per-task** — user directive. Cleaner than the Python
  prototype: opencode's server is the source of truth, so the bridge is near-stateless.
- **Pure in-memory registry, no disk job store** (fable r1) — the bridge is a child of the
  CC session; if it dies the socket/token die with it, so persisted notify-intent points at a
  corpse. Rediscovery comes free from `opencode_list` + the durable title tag.
- **`opencode_send` default `delivery=queue`** (fable r1) — a followup is messaging a busy
  colleague, not yanking the keyboard; steer aborts in-flight tool work.
- **Hand-rolled MCP, not rmcp** — the prior effort was burned by an SDK layout surprise; the
  MCP surface here is tiny (initialize/tools-list/tools-call). fable concurred.
- **Correlation = ownership + `cc-bridge:<origin>:<slug>` title tag + prompt metadata**
  (fable r2). Title is listable in one call (metadata isn't → avoids an N+1 message-scan
  trap). Origin from CC-socket pid survives an MCP-only restart within the same CC session.
- **INVARIANT: origin is a label, never a capability** (fable r2) — pid recycling can only
  mislabel a list entry, never misroute a notification, because notify fires only from the
  live in-process registry.

**Accepted limitations (documented, not engineered around):** a human can type into one of
our sessions via the TUI (foreign turn on a session we own) → we'd report it as ours; two CC
sessions both sending to one rediscovered session. Same class, low stakes.
